# Case 042 - 快速點選套餐子項誤判超過最大選擇數量

## 客服反映內容

店名：[門市/公司]  
POS 版次：v4.X.X  
結帳方式：後結  
線上點餐平台版本：[線上點餐平台]  
線上點餐平台帳號/密碼/檢碼：[SECRET]

客服回報消費者在線上點餐平台點選指定套餐時，套餐組合內的細項商品設定為必選4項，但點到第4項時，偶發性跳出提示：

```text
超過該組合最大選擇數量!!!
```

店家表示昨日與今日都有消費者遇到此狀況，造成現場困擾。

## 查詢結果

### 測試情境

- 套餐：指定 4 人份套餐。
- 組合：指定必選組合。
- 規則：必選 4 項。
- 操作：選擇同一細項商品 4 份。
- 實際結果：跳出「超過該組合最大選擇數量!!!」。
- 正確結果：應可正常加點 4 份。

訂單資訊：

- 訂單識別值：[ID]
- 線上訂單關聯編號：[ID]
- 線上點餐後結銷售單號：[ID]

### 預期結果

不論使用者慢速或快速點擊「＋」4 次，結果都應一致：

- 商品數量：4。
- 不顯示超過上限警告。
- 購物車中只建立同一筆組合明細。

### 實際結果

快速點擊「＋」4 次後：

- 商品數量停留在 3。
- 顯示「超過該組合最大選擇數量!!!」。
- 後端建立了兩筆不同的組合明細。

### 前端紀錄

在點擊事件讀取 前端明細識別值 後加入紀錄，快速點擊時取得：

- 第一次：前端明細識別值 空值，畫面數量 0。
- 第二次：前端明細識別值 空值，畫面數量 1。
- 第三次：前端明細識別值 已帶入，畫面數量 2。
- 第四次：前端明細識別值 已帶入，畫面數量 3。

因紀錄點位於數量加 1 之前，對應送出的實際數量為：

- 畫面數量 0 -> 送出數量 1。
- 畫面數量 1 -> 送出數量 2。
- 畫面數量 2 -> 送出數量 3。
- 畫面數量 3 -> 送出數量 4。

### 後端介面回應判定

錯誤訊息由後端回傳。

HTTP 狀態為成功回應，但 Response JSON 的業務狀態為錯誤：

```text
status: error
message: 超過該組合最大選擇數量!!!
```

前端收到後端回傳的錯誤狀態後，將後端 message 顯示為警告視窗。

### 慢速點擊流程

操作湯底組合，必選 4 項，緩慢點選新增時，前端明細識別值 可正常帶入並累加：

- 第一次：前端明細識別值 空值，數量 0。
- 第二次：前端明細識別值 已帶入，數量 1。
- 第三次：前端明細識別值 已帶入，數量 2。
- 第四次：前端明細識別值 已帶入，數量 3。

慢速點擊時，第一次 後端介面 回傳後，前端會將後端回傳的組合明細 ID 寫回畫面元素。後續點擊都會帶入同一個 ID，因此後端可以辨識這些請求是在修改同一筆組合明細。

### 快速點擊流程

操作菜盤組合，必選 4 項，快速點選新增時，第二次新增來不及帶入 前端明細識別值：

- 第一次：前端明細識別值 空值，數量 0。
- 第二次：前端明細識別值 仍為空值，數量 1。
- 第三次：前端明細識別值 已帶入，數量 2。
- 第四次：前端明細識別值 已帶入，數量 3。
- 隨後跳出「超過該組合最大選擇數量!!!」。

快速點擊時，第一筆新增請求尚未回傳，第二次點擊已經送出。此時前端尚未取得並寫入組合明細 ID，因此前兩筆請求都以「新增組合明細」的狀態送出。

後端因此建立兩筆不同的組合明細：

- 第一筆組合明細：數量 1。
- 第二筆組合明細：後續被更新到數量 3。

第四次點擊嘗試將第二筆組合明細更新為數量 4 時，後端計算同組合總量變成：

```text
第一筆組合明細 1 + 第二筆組合明細 4 = 5
```

因合計超過上限 4，後端回傳「超過該組合最大選擇數量!!!」。

第四筆更新失敗後，第二筆組合明細仍停留在數量 3，因此畫面最後數量停在 3。

### 根因判定

前端問題：

- 「＋」按鈕允許同一商品在前一筆新增請求尚未完成時繼續送出下一筆請求。
- 組合明細 ID 需等 後端介面 成功回傳後才會寫入畫面元素。
- 快速連點期間，前幾筆請求會同時取得空的組合明細 ID。

後端防護問題：

- 後端接受同一購物車、同一套餐商品、同一組合品項在短時間內送出的多筆新增請求。
- 多筆新增請求皆未帶入既有組合明細 ID 時，後端會建立不同組合明細。
- 後端缺少針對此類併發新增的防重、冪等或交易鎖定機制。
